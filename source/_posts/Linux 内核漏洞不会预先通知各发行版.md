2026 年 4 月底，Linux 内核爆出了 CVE-2026-31431 漏洞。这是 IPSec 加密子系统中的一个“释放后重用”漏洞[^1]，它能让任何本地用户直接拿到最高系统管理员权限（root）。这个漏洞早在 2017 年就潜伏在代码里了，当时通过一次代码提交混入了 4.14 版本的内核，随后影响了至今所有的内核版本。修复补丁在 4 月初就已提交到代码上游，但下游的各大 Linux 发行版团队却和吃瓜群众一样，都是通过一家叫 Xint Code 的公司搞的花哨网页才得知此事的。那个网页不仅推销产品，甚至还明目张胆地放了个“下载攻击代码”的按钮。

Gentoo 的开发者 Sam James 在安全邮件列表中直言不讳：“对于 Linux 内核漏洞，除非报告者主动发邮件给各大发行版的联络专线，否则发行版根本收不到任何提前预警。”这次就没人去发这封邮件。于是，RHEL、Ubuntu、SUSE、Amazon Linux 等所有系统的维护团队，都是在漏洞彻底对全天下公开时才如梦初醒。

Hacker News 论坛上瞬间炸开了锅。Xint Code 公司不仅点名道姓地列出了受影响的系统，做了一个非常吸睛的专属网页，还把“获取攻击代码”的按钮紧挨着他们自家 AI 漏洞扫描器的推销广告放着。有网友吐槽，这个披露页面“满满的营销味，根本不像是在做安全”，上面赫然写着“你的软件在 AI 时代安全吗？”，还吹嘘这个漏洞只花了“大约一小时的扫描时间”就找出来了。这家公司有技术搞出这么精美的网页去挨个点名各大系统，却“显然没技术”给这些系统的安全团队发一封预警邮件。不少人发誓要把这家公司彻底拉黑。

但另一拨人则提出了反对意见。他们认为漏洞报告者完全遵守了标准的“90+30”披露策略[^2]。内核主线从 4 月 1 日起就已经包含了这个补丁，报告者也已经通知了内核安全团队。他们还能怎么做？正如一位网友所说，漏洞报告者的责任不是“挨个去通知受影响软件的每一个下游团队”。相比随便一个安全研究员，内核安全团队去协调各大发行版显然更名正言顺。

然而这种辩护很快就站不住脚了。因为 Linux 内核安全团队根本没有，而且按照他们自己的说法也“不能够”，选择性地把安全漏洞提前通知给部分发行版。

Linux 内核的核心维护者 Greg Kroah-Hartman 本尊亲自现身评论区解释原因。首先，内核安全团队的成员都是以个人身份参与的，不代表所在公司，他们不能把安全邮件列表里的任何内容透露给自己的老板。其次，关于通知下游发行版，他反问了一个问题：怎么定义“主要的系统”？如果按用户量算，只有安卓系统（Android）算个角儿，其他全加起来也不过是个微小的误差；如果按收入算，那些付费系统在整个生态圈里也只是极小的一块。最后是更棘手的死规定：内核安全团队与政府和法律机构之间有协议，严禁选择性地提前披露信息。“我们‘绝不被允许’提前通知任何人任何事，否则我们就必须把所有事情告诉所有人，”Greg 写道。这个规定就是二选一的死板：要么谁也不告诉，要么全天下公开。

大家纷纷猜测政府为什么会坚持这种规定。最靠谱的解释是：如果真的存在一个“优先通知名单”，那名单上的所有人基本上就能免费拿到一堆零日漏洞[^3]。那些没在名单上的国家的情报机构绝对咽不下这口气。所以唯一行得通的两条路，要么绝对保密，要么绝对透明。内核安全团队选择了绝对透明。

但是，导致这种信息脱节的深层原因其实和规定无关。好几位安全专家指出，Linux 之父 Linus Torvalds 和 Greg 压根儿就不认为“安全漏洞”应该被当作一类特殊的 Bug（程序缺陷）。他们拒绝给 Bug 定严重等级，也抵制分配 CVE（常见漏洞披露编号）。一位有亲身经历的开发者透露，如果你在提交补丁时用了“漏洞”这个词，你的补丁就会被直接打回。修复本次 CVE-2026-31431 的那次代码更新，就刻意隐瞒了任何与安全相关的影响。下游的系统维护人员根本看不出门道，只会把它当成一次日常的普通代码修改。内核项目组坚持“每个漏洞都只是普通 Bug”的立场带来了非常现实的后果：在更新日志里，安全补丁和所有其他修复长得一模一样。负责维护系统的下游团队，根本得不到任何关于“该优先处理哪个问题”的信号。

这可不是什么理念上的分歧，而是一个实实在在的资源分配问题。对于运行 Linux 的机构来说，代价是惨痛的。一个每周要处理几十个安全漏洞的维护者，不可能有精力去把上游成千上万次普通代码修改都翻一遍。他们需要危险警告信号，但内核团队偏偏就是不给。

当大家还在为流程吵得不可开交时，很大一部分网友表示这些都没意义，因为“漏洞披露”这个问题早就尘埃落定了，只是结果出乎所有人的意料。他们认为，立刻向公众披露，是唯一符合道德的选择。这个漏洞在那儿躺了九年了，你不知道它，不代表它不存在。公开披露能让防守方立刻采取行动，并倒逼厂商更快地打补丁。不少人把所谓的“负责任的披露”称为微软等大厂搞出来的洗脑骗局，目的就是为了控制研究人员、保护公司面子。一位资深安全研究员直言不讳：“根本不存在所谓‘不负责任的披露’。”另一位网友提到了之前的先例：补丁发布的同一天，直接放出完整的攻击代码。

而真正负责维护系统的一线运维人员，给出了更现实的抱怨。“在攻击代码公开和补丁真正应用到生产环境的这段空窗期里，鬼知道有多少云主机服务商被黑了。”对于一觉醒来发现服务器被黑的系统管理员来说，那些形而上的哲学讨论根本毫无安慰可言。

不过，另一拨安全工程师对整个讨论的前提提出了质疑。他们说，问题根本不在于什么时候披露，或者发行版之间怎么协调。真正的问题在于，大家居然把 Linux 内核本身当作了一道坚不可摧的安全边界。内核级别的本地提权漏洞根本不稀奇，它们在网络黑客圈早就成了“烂大街的便宜货”。任何仅仅依靠基础容器技术或 Unix 用户隔离机制来区分不受信任客户的云主机服务商，“早就输在起跑线上了”。真正的安全隔离至少需要用到虚拟机，最理想的是使用专门构建的强隔离层（比如 Firecracker 等）。如果你把一堆互相防备的程序放在同一个内核下运行，世界上再好的披露策略也救不了你。

有人反驳说，在实际应用中，使用基础容器进行隔离的做法比比皆是。连大名鼎鼎的 Kubernetes 默认也不采用严格的虚拟机隔离模式。安全圈的正统理论和行业的实际做法之间有着巨大的鸿沟，直接把整个共享主机行业贬低为“玩忽职守”，并不能解决当下的麻烦。但那些持怀疑态度的人提出了一个难以反驳的观点：就算有完美的漏洞披露流程，内核提权漏洞依然会存在，整个行业的底层架构依然脆弱不堪。

当政策辩论还在如火如荼地进行时，网管们已经在着手解决实际问题了。帖子里最有用的其实是那些技术贴。之前邮件里附带的“禁用模块”临时方案，只对少数特定内核有效。而像 RHEL、Fedora 和 Gentoo 等好几个主流系统，是把该功能直接焊死在内核主程序里的。针对这些系统，有人发了修改底层启动参数的临时招数。还有大佬直接发布了一个已经在生产环境中跑起来的、基于 eBPF 技术[^4]的高级拦截方案。有网友还指出了一个会坑死人的细节：内核会在需要时自动静默加载危险模块，所以你用查看命令没看到它，不代表你就安全了，你必须主动出击去禁用它。

另外，这个修复补丁很难直接平移硬塞到旧版本的长期支持内核上。因为新旧版本代码差异太大了。Gentoo 开发者也承认，即便是干劲十足的系统维护者，也没有把握把补丁强行打在急需上线的服务器上。采用临时禁用方案，已经是两害相权取其轻了。

帖子里还引发了一场关于漏洞攻击代码本身的小插曲。公开的验证代码（PoC）[^5]依赖于利用缓存漏洞读取某个高权限文件，因此，只要取消这类文件的“全局可读”权限，就能防住这个现成的攻击脚本。但许多网友指出，该漏洞能搞到系统最高权限的路子多了去了，远不止公开代码演示的那一种。仅仅堵住这一条路，根本不叫真修复。

那么，整个 Linux 生态系统出路在哪儿呢？讨论中大家提出了一些改革建议，但没一个是容易搞定的。有人认为，各个发行版应该放弃自己维护的内核版本，直接完全同步上游更新。这将彻底解决“没法区分优先级”的问题，反正安全补丁和其他常规更新大杂烩一起更。反对声音则说：系统厂商维护自己的版本是有硬性原因的——要保证老系统稳定、要兼容旧硬件、要兑现给客户的长期服务承诺。不能因为挑出安全补丁太难，就把这些现实需求全盘否定了。

还有人提议搞一个核心系统的联系名单，专门用来提前发安全通知。显而易见的候选人包括那些作为很多衍生系统祖宗的巨头。但这直接撞上了之前提到的政策红线，以及“谁来拍板定名单”的世纪难题。有网友调侃说，干脆用市场手段解决协调难题：那些签了商业支持合同的系统厂商，完全可以花钱雇人混进内核安全团队，以此来“内部”获取通知。

一个相对温和且靠谱的建议是：内核项目组至少可以把与安全相关的代码更新打个标签，而不是刻意掩盖它们的安全属性。这样既不需要选择性泄密，也不用改变现有的死板政策。下游系统维护者就可以根据实际风险来排班打补丁，不用天天瞎猜了。

这次漏洞事件暴露出，Linux 生态系统正夹在三方诉求之间，谁也没法完全如愿。内核项目组一视同仁地对待所有 Bug；系统发行方需要根据严重程度来安排修复优先级；普通用户需要赶在攻击代码满天飞之前拿到补丁。内核项目受法律约束不能搞特殊化提前通知；系统发行方没收到危险预警根本无从排查；而漏洞既然已经潜伏了九年，用户也不可能遥遥无期地干等着各方慢吞吞地去协调。

到头来，被坑得最惨的既不是内核开发者，也不是系统维护商，更不是安全研究员。而是那些苦逼的一线运维网管。他们通过一个花里胡哨的推销网站才知道自家服务器出了最高危漏洞，然后手忙脚乱地去学习部署冷门的拦截方案，生怕慢一步，自己管理的机器就被别人用网上的现成代码给黑了。在这个链条上，每个人都在做符合自身利益和规则的事情。最终，所有的烂摊子都重重地砸在了链条最末端、最无力改变现状的人头上。

[^1]: 释放后重用（Use-after-free）：一种常见的内存破坏漏洞。指程序在使用完某块内存并将其释放后，没有清空指向该内存的指针，导致后续还能继续使用这块已被回收的内存。黑客常利用此漏洞在内存中植入并执行恶意代码。
[^2]: 90+30 披露策略：安全圈的一种国际惯例和行规。指安全研究员发现漏洞后，给软件厂商 90 天的时间进行修复；补丁发布后，再留 30 天让广大用户升级更新，之后才将漏洞的技术细节向公众全盘托出。
[^3]: 零日漏洞（Zero-day）：指那些已经被黑客或研究员发现，但官方还没发布补丁修复的严重漏洞。因为软件方只有“0 天”的时间来反应和防御，非常危险，在黑客地下市场价值极高。
[^4]: eBPF：一种可以在不修改操作系统源代码、也不重启系统的情况下，安全高效地在操作系统核心层运行自定义程序的技术。近年来常被运维人员用来做系统级的快速底层监控和防护。
[^5]: PoC（Proof of Concept）：概念验证代码。指安全研究员为了证明某个漏洞确实存在且可被利用，而编写的一小段演示性攻击代码。常常被黑客直接拿去改装成真正的武器。
