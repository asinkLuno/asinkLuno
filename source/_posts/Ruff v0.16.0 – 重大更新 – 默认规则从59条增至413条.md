Ruff 0.16.0 版本将默认规则数量从 59 条猛增到了 413 条。整整七倍的增长，在 Astral 团队看来绝对是一件好事：能抓出更多 bug，减少配置项，还能让新项目毫不费力地获得安全保障。从 0.1.0 版本至今，这个工具的总规则数已经从 708 条涨到了 968 条。官方的发布公告认为，增加默认规则是顺理成章的下一步。毕竟，很多能捕捉语法错误和运行时 bug 的规则，仅仅因为没人知道，就一直处于闲置状态。这种逻辑听起来无懈可击。但在 Hacker News 上关于这次发布的讨论中，可以看出社区对于"默认规则变多到底好不好"存在严重分歧。这种分歧也暴露出了更深层的问题：代码检查工具（`Linter`）到底是用来干嘛的？又是为谁服务的？

最直接的反对声音来自那些维护老代码库的开发者。如果你的项目昨天在 59 条规则下还是干干净净的，今天在 413 条规则下，几乎肯定会"满地飘红"。正如一位评论者所说，这意味着会涌现出一大堆代码合并请求（`Pull Requests`），它们啥也没干，纯粹只是为了满足前一天还不存在的规则去格式化代码。官方文章里只用了一句话来回应这种矛盾，告诉大家怎么退回旧版的默认设置。但讨论区的反应很明确："在配置文件里加个选择条款就行了"这种说法根本没抓住重点。问题不在于恢复旧设置有多难。问题在于，Ruff 一边标榜自己是"零配置"工具，一边又发布破坏性更新，逼着所有老用户要么去改配置，要么手忙脚乱地去修复成千上万个新警告。这两个目标完全是自相矛盾的。

Ruff 的版本发布策略让这种矛盾变得更加尖锐。好几位评论者都感到很沮丧，因为 Ruff 明明已经在生产环境中用了好几年，主版本号却依然是 0。按照语义化版本控制（`Semver`）对 0.x 软件的规定，这就允许它在次版本更新中引入破坏性改动。从技术上辩护是没毛病的：`Semver` 确实明确允许这种做法。但大家情绪上的抵触并不是因为技术对错，而是关乎信任。当你每天运行几百次的一个工具，一个已经吞噬了 `Black`、`Flake8` 和 `isort` 市场份额的工具，仍然自称是 v0.x 时，它的每一次小版本更新都会让人闻到一种不稳定的气息。有评论建议 Ruff 借鉴 `Nix` 的 `stateVersion` 机制：你可以声明自己想要哪套默认规则，等团队准备好了再从容升级。另一个人则干脆建议锁死版本号，等方便的时候再升。对于官方文章根本不觉得是个事儿的问题，这两种做法都是非常实用的权宜之计。

除了版本号的争议，大家还爆发了一场更基础的争论：代码检查工具最初到底是用来干嘛的？一位有着 20 年 Python 经验的评论者指出，他从来没见过哪个真正的 bug 是因为模块导入没排序，或者用了一个空的 `except` 捕获异常而引起的。开启所有规则，只会产出一些在技术上合规，但在关键逻辑上依然烂透了的代码。他描述了自己亲眼看到的一些公司：死磕每一条 Ruff 规则，最终交付的代码虽然排版漂亮，但漏洞百出且根本没法维护。这种批评并不是说 Ruff 的本职工作做得很差。而是指 Ruff 检查的往往是表面文章，跟软件质量没多大关系。而整个行业对这些表面功夫的痴迷，不过是披着专业外衣的"货物崇拜编程"[^1] 罢了。

讨论区里的反面意见同样激烈，而且源于另一种不同的经验。几位评论者描述了代码检查工具普及之前的日子。那时候，团队会为了该用 `Tab` 还是空格吵上好几天。代码合并请求总是陷入代码风格的讨价还价中。项目失败，仅仅是因为不同的开发者用了不同的编辑器设置，导致文件出现了微妙的不兼容。这里的论点不在于某条具体规则重不重要，而在于"一致性"本身很重要。而且，只有靠自动化强制执行，才能在不浪费人力的情况下保证这种一致性。有位评论者把代码检查工具比作疫苗：当它们发挥作用时，你就再也看不到它们解决的问题了，于是你很容易忘记以前的情况有多糟。从这个角度看，Ruff 增加默认规则不仅不是在强加于人，反而是一份礼物。这意味着新团队一开始就能拥有一套广泛、合理的规范，不用再从头扯皮了。

这两拨人其实不是在争论 Ruff。他们是在争论"和别人一起写代码"到底意味着什么。反代码检查阵营把编程看作一门手艺，一种个人的艺术形式，表达方式和意图非常重要。如果一个工具分不清什么是刻意的排版设计，什么是真的写错了，那它从根本上就是反人类的。挺代码检查阵营则把编程看作一项团队运动，在众多贡献者之间保持代码的可读性和可预测性，远比任何个人的喜好更重要。把无聊的部分自动化，才能让人腾出精力去解决真正的难题。这两种立场都有其自洽的逻辑，也都反映了现实中的取舍。而 Ruff 显然无法同时满足双方。

官方文章还介绍了一些争议没那么大的纯新功能。比如支持 `Markdown` 代码块格式化，这就把 Ruff 的触角伸向了文档和 `Quarto` 笔记本。新增的 `ruff: ignore` 和 `ruff: file-ignore` 忽略注释，让开发者能更细粒度地控制哪些规则在哪些地方生效。修复代码时的差异对比现在也会直接在终端输出里显示了，不用再单独加个 `--diff` 参数。不管你在哲学理念上站哪边，这些都是实打实的改进，让这个工具在实际工作流中变得更好用了。特别是"忽略注释"这个功能，直接解决了反代码检查阵营的一个核心痛点：如果某条规则对你刻意写的某段代码报了警，你现在只需加一行注释就能让它闭嘴，顺便还能把你的思考理由写上。文章里重点宣传了这个功能，但讨论区里几乎没人提。这说明大家的怒火一直都是冲着"扩充默认规则"去的，而不是工具本身的能力问题。

讨论区里唯一一个几乎全员同意文章观点的方面，就是性能。好几个人分享了测试数据，显示 Ruff 在几万行代码的库中，只需几毫秒就能返回结果。它找出几百个问题的速度，比老工具解析文件还要快。其中一个与 Go 语言生态里 `golangci-lint` 的对比尤为扎心：Go 语言的这个代码检查聚合器，即使有缓存，在持续集成（`CI`）里也可能要跑上几分钟，而 Ruff 只需要几秒甚至零点几秒就能搞定。这种性能优势正是 Ruff 能够取代那么多老工具的原因，这一点毫无争议。即使是帖子里批评最狠的人，也还在继续用 Ruff。大家的分歧在于默认设置和理念，而不是这个工具做得好不好。

讨论中出现的与 Go 语言生态系统的对比很值得深思。Go 有一个叫 `gofmt` 的工具，它出了名的强势、简单，而且被普遍接受——原因恰恰是大家都一样讨厌它。但 `gofmt` 并不算很严格。它只处理基础的格式化，留下了很多变通的空间，这也导致后来又冒出了 `gofumpt` 和 `golines` 等一堆试图填补空白的附加工具。Go 还有 `golangci-lint`，它打包了几十个检查工具，但因为本质上还是在运行多个独立的工具，所以难免有性能问题。好几个评论者都明确表示，真希望 Go 也能有个像 Ruff 一样的东西：一个极速的单一程序，把格式化和代码检查全包了，不用再经历把各个独立工具东拼西凑的配置噩梦。从这个角度来看，Ruff 已经不单单是个 Python 工具了。它成了所有编程语言生态想要拥有的一种工具典范。而 Python 生态居然靠着一个用 `Rust` 语言写的程序捷足先登，这不过是一次让其他语言社区羡慕不已的历史偶然。

官方文章里说的单纯改进，和讨论区里揭示的复杂权衡，其实是站在不同高度看同一件事。在发布博客的高空视角下，413 条默认规则代表着数字的增长，而大家总是喜欢"增长"的。但在落地的实操层面，每一条新加的默认规则，都是在替成千上万个项目做决定，而这些项目的维护者根本没有参与决策的权利。官方文章的逻辑建立在一个假设上：规则越多 = 抓出的 bug 越多 = 软件越好。但讨论区从各个层面挑战了这个假设，既有现实层面的（"这搞崩了我的 `CI` 流水线"），也有哲学层面的（"这里头一半的规则根本找不到真正的 bug"）。双方都没有错。Ruff 未来的挑战在于，既要保持让它称霸江湖的极高运行效率和打磨质量，又要想办法找到一个合理的版本控制和默认设置策略，别让每个用户在每次更新时，都把这场争论再重新演练一遍。

[^1]: 货物崇拜编程（`Cargo-cult engineering`）：科技圈俚语。用来讽刺那些根本不理解背后原理，只知道盲目照搬别人做法（比如死磕代码排版），并迷信这样就能写出好软件的行为。字面意思是二战时太平洋岛民看到美军飞机带来物资，战后就用木头搭建假飞机，迷信这样能再次把物资盼来。
