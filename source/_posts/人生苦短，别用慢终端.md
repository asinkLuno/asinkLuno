如果你一整天都在终端里敲代码，哪怕一毫秒的卡顿也会积少成多。切标签页时的卡顿，自动补全时那半拍的延迟，或是命令提示符弹出来之前的短暂停顿。单独看，这些都不算什么。但如果每天经历几百次，它们就会不断消耗你的注意力。为了解决这个问题，Mijndert Stuij 打造了一套配置：一个启动只需 30 毫秒的 shell，以及一个完全跟得上打字速度、毫无延迟的终端模拟器。

Stuij 的第一条建议最简单：抛弃那些臃肿的框架。别用 `oh-my-zsh`[^1]，别用 `prezto`，也别用插件管理器。他直接从本地硬盘加载三个插件，彻底避开了启动时那些解析依赖关系的复杂框架。讨论帖里呼声最高的那批网友，早就通过性能分析得出了同样的结论。有些人做得更绝。有个人直接用 `NetBSD sh`[^2]，连终端模拟器都不用，就跑在纯 `VGA` 文本模式下，没有显卡驱动，也没有桌面环境。还有个人仅仅是注释掉了一个从没用过的工具链管理器，就把启动时间从 390 毫秒缩短到了 80 毫秒。大家都在反复印证同一个道理：你加载的每一行代码都是有性能成本的，而那些大而全的框架，很容易让你为从没用过的功能“买单”。这根本不是什么写出多精妙的启动脚本的问题，而是从一开始就别往里塞那么多垃圾。

这篇讨论帖还把原文章里的基准测试（`benchmark`）挑了刺。Stuij 为了测试 shell 的启动速度，写了个循环跑 `zsh -i -c exit` 然后记录总耗时。好几个人指出，这根本测不出你想看的数据。Romkatv 开发的 `zsh-bench` 工具就把延迟分得很细：首次提示符延迟、命令延迟和输入延迟，这些才是你真正能“感觉”到的卡顿。有个人用着一台便宜的笔记本，把提示符延迟压缩到了 5 毫秒以下，输入延迟控制在 1 毫秒内。这些数字才是关键。至于单纯退出 shell 需要多长时间，其实没那么重要。Stuij 在当天就发了一篇跟进文章，坦诚地梳理了自己弄错的地方。这点值得点赞。整个事件也是个很好的提醒：测量终端的性能比看起来要复杂得多。如果你优化错了指标，很可能只是“看起来很快”，但在关键环节依然卡得要命。

接下来就是跑分也解决不了的分歧了。大约有一半的评论者每天只打开几次终端，然后就一连几周都挂在 `tmux` 会话里。对他们来说，shell 的启动时间根本无所谓。有个人说自己常驻四个 `tmux` 会话，每个都有专门的用途，他几乎从来不打开全新的终端窗口。另一个人写了个开机脚本自动排好标签页，之后就彻底忘了启动这回事。而另一半人则是疯狂地打开、关闭终端。一位 SRE 说自己经常要同时处理十几个不同的任务，为了保持专注，他会为每一个任务场景开一个新终端。还有人列出了自己典型的日常操作：用 `lazygit` 快速查一下代码，开个阅后即焚的 `LLM`（大语言模型）会话调试一下测试代码，用 `vim` 快速改个文件，再用 `fzf` 搜一下文件。这里的每一步都在开新终端。如果每开一次都要卡上半秒钟，那绝对能把人逼疯。

关于子 shell（`subshell`）[^4] 的讨论让大家的视野更开阔了。哪怕你从来不开新的终端窗口，你用的各种工具也在后台不停地创建子 shell。比如 `Vim` 里的 `:terminal`，或者跑 `GNU Make`、`Tmux` 还有各种 Shell 脚本的时候。虽然交互式和非交互式 shell 加载的启动文件不一样，但这笔性能开销从来就不会是零。在 `Cygwin`[^5] 环境下，创建一个新进程（`fork`）的代价极其高昂，因此想方设法避开没必要的子 shell 就成了基本功。Shell 启动的性能成本，不光是你眼前能看到的那个窗口，你工具链在后台悄悄启动的每一个子 shell，都在默默消耗着系统资源。一位网友总结得很到位：“终端窗口，一天开几次；但 Shell，每隔几分钟就会启动一次。”

在整个讨论帖中，Stuij 针对 `nvm`[^6] 给出的懒加载（`lazy-loading`）技巧获得了最一致的好评。他用一个 shell 函数把 `nvm` 包装起来：当你第一次调用它时，这个函数会先把自己删掉，然后加载真正的 `nvm` 脚本，并把你的命令参数传过去。也就是说，只有第一次使用时会稍微卡一下（交点“过路费”），之后就已经是加载好的状态了。大家立刻举一反三，把这招用在了 `pyenv`、`kubectl` 以及任何要求你在配置文件里塞一句 `eval "$(tool init zsh)"` 的工具上。有一位只偶尔碰碰 JS 工具链的 Rust 和 C++ 开发者，利用 zsh 的 `autoload` 功能把 `pyenv` 的加载推迟到了第一次使用时。还有人用别名（`aliases`）的方式，把 `nvm` 的启动成本从 shell 刚打开时，转移到了第一次敲 `node` 或 `npm` 命令的时候。这一招不仅巧妙，而且非常百搭。

不过，帖子底下一个讨论非常热烈的楼中楼里，大家对“妥协使用 `nvm`”这个想法本身提出了质疑。既然能把这块毒瘤割掉，干嘛还要打补丁呢？好几个人推荐用 `fnm` 来替代，速度更快，而且可以无缝切换。更多的人推荐了 `mise`[^7]，这个工具把 Node、Python 和环境变量管理全打包在了一起，甚至还能顺手把 `direnv` 也给替换掉。当然也有人指出了它的缺点：`mise` 配置文件满天飞，有时候挺烦人的。一位曾经用 `Volta` 的用户就很不爽，因为 `Volta` 被拿掉换成了 `mise`。另一位则抱怨说，既然 `package.json` 里都已经锁定了 Node 版本，干嘛还要再折腾一个额外的配置文件。总之，大家确实都在从 `nvm` 往 `mise` 迁移，但这确实有一个免不了的阵痛期。

Stuij 推荐的一款叫做 `Pure` 的异步 `git` 提示符，算是帖子里很多人淘到的真宝贝。有人坦言，自己以前压根不知道 `zsh` 还能更新已经打印出来的提示符。在体积庞大的代码仓库里，跑一次 `git status` 可能要花十秒钟甚至更久。如果没有异步加载，你每次敲回车都得干等这么长时间。而 `Pure` 会瞬间把命令行提示符画出来，等后台把 `git` 信息拉取完毕后，再填补上去。它硬生生地把一个显眼且烦人的卡顿源，变成了你用起来根本毫无察觉的东西。一位用 `fish` shell 的用户提到，自己也折腾过类似的异步 `git` 配置。可见这个思路并不局限于 `zsh`，但很多读者确实是看了 Stuij 的文章，才知道原来还能这么玩。

关于终端模拟器本身的讨论就更是吵翻天了。Stuij 力挺的是 `Ghostty`[^8]——由 Mitchell Hashimoto 开发的一款 `GPU` 加速终端。Hashimoto 本尊竟然亲自现身帖子，直接回应了关于性能的吐槽，并要大家提供可以复现的跑分数据。有些用户说 `Ghostty` 空闲时 `CPU` 占用几乎为零，手感非常干脆。但也有人表示，在负载较重的情况下，它比老牌的 `iTerm2` 还要卡。一位 Arch Linux 用户直言它“比 `Kitty` 慢得多”。甚至有人戏称它是“`TTY` 界的游戏驿站（`$GME`）[^9]”，就跟那些迷因股票一样，热度全靠创始人的名气撑着，而不是靠技术。不过 Hashimoto 本人的态度倒是很客观冷静：他认为 `Ghostty` 和 `Kitty` 都在“快”的第一梯队里，你没必要纠结它俩谁更快，直接根据你需要的功能去选就行了。

这里的每一个替代品都有自己的拥趸。`Kitty` 的用户喜欢它的速度和成熟度。`WezTerm` 的粉丝看中它内置了终端复用功能。而仅支持 Linux 和 `Wayland`[^10] 的 `Foot`，在冷启动速度上直接干翻了 `Ghostty`，原因就在于它功能简单，所以优化得更极限。`Foot` 既能独立运行，也能以后台守护进程（`daemon`）模式运行，任你挑选。不过大家对守护进程模式褒贬不一。`Ghostty` 是单进程运行的，而好几个人都曾在 `urxvt` 和 `foot` 的 `C/S`（客户端/服务端）架构上吃过亏：后台进程一崩溃，所有的终端窗口瞬间全军覆没。为了稳妥起见，他们又乖乖换回了独立运行模式。这一切讨论的结论是：终端性能极度依赖于你系统的底层环境。纯粹的速度只是一个维度。稳定性、功能丰富度，以及你的平台支持什么，所有这些因素综合在一起，才决定了你真正感觉到的“快”。

还有一小拨人提出了一个灵魂拷问：给终端搞 `GPU` 加速真的有意义吗？你就是在屏幕上显示几个纯文本而已，凭什么还要牵扯到显卡驱动？这就好比前面提到的那个在纯文本模式下用 `NetBSD sh` 的老哥，没有桌面环境，没有图形界面库，更不用显卡。他的整个操作系统就是围绕纯文本搭建的。这虽然是一种很极端的立场，但也一针见血地指出了一个事实：文章里讨论的“终端”，潜台词已经假定了你用的是一套特定的现代技术栈，而这套技术栈本身，就带有无法避免的依赖和性能开销。

讨论中还带出了一些原文章忽略的性能视角。有人说，只有当程序往屏幕上疯狂输出一堆长篇大论的日志时，他才会注意到终端的速度。这就说明，数据吞吐量也很重要。对于海量输出内容的渲染速度，是除了“启动时间”和“输入延迟”之外的第三个核心维度。对于某些工作流来说，这个指标极其重要，特别是当你在同时处理多个并发进程的时候。还有人提到了复杂文本的渲染问题。无论是 `Ghostty`、`Kitty`、`Alacritty` 还是什么 `GNOME` 终端、`xterm` 等等，在渲染高棉语（Khmer）[^11]时全军覆没。只有 `Cosmic term` 能正确渲染元音附标文字（`abugidas`），但它在老旧硬件上又卡得像幻灯片。实际上，“正确性”也是性能的一部分。如果你的终端连字都显示得缺胳膊少腿，那它连唯一的本职工作都没做好，哪怕你敲键盘反馈再快又有什么用呢？

当然，帖子里也有轻松搞笑的一面。有个人亮出了自己 0 到 10 毫秒的启动跑分，然后一本正经地嘲讽道：“30 毫秒也太慢了吧。”另一个人开始纠结，要不要把自己那套花里胡哨的启动脚本给删了——那脚本每次打开终端都要连环调用 `fortune`、`cowsay` 和 `lolcat`[^12]，在后台疯狂启动子 shell、Perl 和 Ruby 环境。但他最后觉得，如果为了优化性能而丢掉这点生活情趣，那不优化也罢。还有人干脆在评论区敲了一句 `echo $bait > /dev/null 2>&1`[^13]，疯狂暗示这整篇文章就是个钓鱼帖（troll）。不得不说，当优化到了某个临界点，收益确实是直线下滑的。在“关心趁手的工具”和“魔怔地刷跑分”之间，只有一线之隔。

这篇热帖与其说是对 Stuij 的方案下了一个最终判决，不如说是给大家画了一张性能优化的全景地图。他的核心观点依然立得住脚：你得清楚自己加载了什么，算算它们要消耗多少性能，然后果断扔掉那些你用不上的东西。但是，评论区的讨论让他的每一个具体建议都变得不再那么绝对了。你可以用 `nvm`，但最好用懒加载；或者干脆别用了。你可以用 `Ghostty`，也可以用 `Kitty`，或者 `Foot`，甚至什么模拟器都不用。给自动补全加上缓存，除非你在用 `fish`，因为它原生就处理得很好。没错，优化启动时间是有意义的，但提示符延迟和输入卡顿更重要，而且 `zsh -i -c exit` 根本不是正确的跑分姿势。这场讨论把一个人的工作流，拆解成了一张所有人都能参考的“权衡利弊表”。这可比塞给你一服包治百病的灵丹妙药要实用得多。你每天一睁眼就泡在终端里，去关注它的性能好坏，这本身就是意义所在。至于到底走哪条路，完全取决于你的工作习惯、你跑的代码，以及你对折腾这些破事儿的容忍度到底有多高。

[^1]: `oh-my-zsh`: 一个极受欢迎的 `Zsh` 配置管理框架，内置了海量好看的主题和方便的插件。虽然一键变漂亮很简单，但插件装太多会导致终端每次打开时奇慢无比。
[^2]: `NetBSD sh`: 一种非常古老、极致精简的操作系统内置命令行工具。完全没有花里胡哨的现代功能，主打一个原汁原味和极致轻量。
[^3]: `tmux` 会话 (`tmux` sessions): 一款终端里的”分屏神器”兼”后台保活工具”。它可以让你在一个窗口里切出好几个小黑框，而且就算你不小心关掉了终端软件，里面的任务仍会在后台运行，下次打开还能无缝连上。
[^4]: 子 shell (`subshell`) 与 `fork`: 在操作系统中，`fork`是系统为了执行新任务而复制出一个新进程的动作；而”子 shell”就是当前环境派生出来的全新独立环境。这个复制和新建的过程是非常消耗电脑计算资源的。
[^5]: `Cygwin`: 一个能让 Windows 系统像 Linux 一样运行各种命令行工具的底层模拟环境。因为两套系统的核心机制”水土不服”，它在创建新进程（`fork`）时极其吃力。
[^6]: `nvm` / `fnm` / `pyenv`: 统称”版本管理器”。因为程序员做不同项目时常需要不同版本的编程语言（如 Node.js 或 Python），这些工具能让你随时切换版本。但它们出了名地会在终端启动时拖慢整体速度。
[^7]: `mise`: 一个近年崛起的新生代工具，把原本分散的各语言版本管理和环境变量管理全打包在了一起，主打一个速度快且”多合一”。
[^8]: `Ghostty` / `Kitty` / `WezTerm` / `Foot`: 这些都是”终端模拟器”（即你打开的那个黑框框软件本身）的名字。它们各有所长，有的主打用显卡加速（`GPU` 加速）让打字极其丝滑，有的主打纯粹的高性能，有的主打功能丰富。
[^9]: `$GME` (游戏驿站): 美股市场里最著名的”迷因股（Meme stock）”之一，曾因散户抱团炒作而暴涨脱离实际价值。这里是网友在阴阳怪气地讽刺某个终端软件名不副实，热度全靠粉丝炒作。
[^10]: `Wayland`: Linux 系统下新一代的显示服务协议，旨在替代老旧的 `X11`。在这个环境下的软件通常需要更现代化的专门适配。
[^11]: 高棉语 (Khmer text) 与 元音附标文字 (abugidas): 东南亚等地区使用的一种复杂文字系统。其排版逻辑很特殊，字母和音标需要上下左右相互交叠组合，很多缺乏深度优化的现代终端根本无法正确显示它们。
[^12]: `fortune`, `cowsay`, 和 `lolcat`: Linux 命令行里经典的”摸鱼三件套”。连起来用的效果是：每次打开终端，都会有一只用符号画出来的牛（`cowsay`），吐出一句随机的名人名言（`fortune`），而且字体全都是亮瞎眼的彩虹色（`lolcat`）。
[^13]: `echo $bait > /dev/null 2>&1`: 程序员专属的冷笑话代码梗。在 Linux 中，把东西扔进 `/dev/null` 意思是”丢进黑洞直接销毁”。网友把文章比作”鱼饵（`bait`）”，意思是”别信他，这家伙就是故意发个性能话题的钓鱼帖来骗回复的”。
