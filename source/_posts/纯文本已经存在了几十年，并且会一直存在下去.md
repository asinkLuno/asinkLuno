这场讨论围绕着一篇文章展开，文章探讨了一类小众却十分“倔强”的软件：用来画图表和 UI 原型的纯文本工具。文章点名了三个代表：Mockdown、Wiretext 和 Monodraw。有了它们，你就能用等宽字符画出排版、流程图和架构图。靠的是制表符、破折号、竖线，偶尔还夹杂点 ASCII 字符画。文章很看好这类工具，原因有几个：首先，它们复兴了一种在 Turbo Vision[^1] 和 DOS 文本模式时代达到顶峰的界面风格；其次，它们刻意给自己“设限”，而在电脑性能越来越强悍的今天，这种限制反而显得别具一格；最后，它们证明了纯文本并没有过时，它不仅是一种存储格式，更是一种思考方式。

这篇文章下面 Hacker News 的评论区，也发挥了优质评论区的传统艺能：越聊越宽。网友们纷纷查漏补缺、指出矛盾，甚至“掀底牌”[^2]。最直观的贡献就是，大家把文章里提到的三个工具扩充到了十几个，接着变成二十几个，最后干脆弄出了一个“大全”网站 `https://xosh.org/text-to-diagram/`。甚至连 D2 测试版里的 ASCII 输出模式都被挖了出来。接着，终端绘图工具也加入了群聊：gnuplot 的哑终端模式[^3]、feedgnuplot、bashplotlib、ttyplot、visidata 统统上榜。还有人想起了 DOS 时代 MINITAB 统计软件用文本字符拼出来的散点图。整个评论区变成了一个活生生的工具目录，比起原文，它更好地证明了文章的观点：这个生态圈可远不止三个工具那么简单。

不过，评论区也暴露了一个根本性的误解：文章里用的那些术语到底是什么意思？文章把这些工具叫作“纯文本”或“ASCII”工具，然后加了点免责声明。它对“ASCII”的用法，就像现在大家不管三七二十一，把所有循环播放的短视频都叫“GIF”一样，纯属口语化表达。好几个网友对此提出了异议。这些工具最核心的制表符根本不是 ASCII 码。它们出自 Unicode，如果再往前追溯，是来自 IBM 的 Code Page 437[^4]（CP437）。CP437 只能勉强算是“扩展 ASCII 码”，而历史上相互冲突的扩展 ASCII 编码可太多了。一位 Roguelike 游戏[^5]圈的网友提到，现在大家看到满屏幕 CP437 字符、甚至完全是图形化瓦片地图的截图时，也会习惯性地夸一句“这 ASCII 艺术真棒”。几十年来，这个词的意思早就跑偏了。文章对“ASCII”的随性用法确实符合大众日常习惯，但网友的较真也说明了一点：对于那些清楚知道 ASCII 表在哪结束、制表符区块从哪开始的工程师来说，这听起来完全不是一码事。

这个术语上的混乱反而引出了更有意思的话题。有网友提到了 Dylan Beattie 的演讲《世上压根没有纯文本这回事》。演讲的核心观点是：我们所谓的“纯文本”，其实底下藏着一层又一层的技术决策。是码位还是字形[^6]？是编码方式还是字符集？用 UTF-8 还是 UTF-16？带不带 BOM[^7]？另一位网友解释得更精准：Unicode 是把数字映射到码位，而不是把字节映射到字符，而且有些字符需要多个码位组合才能表示。搞定这些后，你还需要一种编码方式把数字变成字节。所以，到底什么是纯文本？是 UTF-8 吗？带 BOM 还是不带？评论区里，一拨人觉得这事儿早就定论了：UTF-8 已经赢了，闭着眼睛当它是 UTF-8 就行，99.7% 的情况下都不会出错。另一拨人立马甩出证据：Excel 现在默认导出的 CSV 还不是 UTF-8 格式呢；PCL 打印流[^8]能在一个文件里混用好几种不同的扩展 ASCII 编码；而且只要文本里全是 7 位字符，它在任何编码下长得都一模一样。乐天派看准了发展趋势，而怀疑论者则死死盯着那些容易翻车的极端情况。纯文本这东西，在没出幺蛾子之前，看着挺简单的。

紧接着的一个争议点是：就算编码不出问题，光用纯文本够用吗？有网友觉得，纯文本意味着每次都得从零开始：没有数据模式，没有验证机制，没有统一的结构标准。临时写点 Unix 管道[^9]命令处理数据确实爽，但它终究替代不了真正的格式。不过，更让人信服的反驳是“对，而且还可以更进一步”。Markdown、JSON、YAML、OrgMode、LaTeX——这些东西骨子里都是纯文本。你可以用 grep 和 awk 一行行地搜它们、处理它们，也可以把它们解析成结构化数据，渲染得漂漂亮亮。结构化和非结构化并不是非黑即白的单选题，它是一个渐变的光谱，而真正有意思的工作往往发生在两者之间。

原文有一点说得很对，评论区也几乎全票赞成：纯文本经得起时间的考验。有网友搬出了林迪效应[^10]：文本可是和 SQL 以及 TCP/IP 一起活到今天的。还有人引用了 Graydon Hoare 那篇著名的老文章《永远押注文本》。第三个人说得更直白：“纯文本存在了几千年，只不过以前它不是数字化的而已。”网友们也分享了自己的实战经验。有人拿纯文本记了 20 年笔记；有人用了 7 年纯文本开发票；还有人把个体户的账本从 QuickBooks 搬到了 Beancount 加 Fava[^11] 上，还用 Git 搞了一套带 RFC3161 时间戳认证的审计追踪。这些可不是什么怀旧情结。大家真金白银地用纯文本工作流来经营业务，就图它速度快、透明，而且永远不用担心被软件厂商抛弃。一个 1994 年的 `.txt` 文件，今天照样能顺畅打开。这可是任何私有格式都做不到的。

文章的另一个论点——“限制本身也是一种功能”，引发了评论区最精彩的一场哲学辩论。文章认为，随着 AI 让电脑变得越来越万能，这种“限制”反而更重要了：我们需要刻意给自己设限，把事情变难，而不是变容易。有网友把这个观点拆解开来，区分了什么是“限制带来的不可能”，什么是“限制带来的不合理”。英语盲文为了省地方，会把常用词压缩成简写。ColorForth[^12] 编程语言用颜色来缩短源代码。Unix 把“move”缩写成“mv”，把“copy”缩写成“cp”。这些都不是因为条件不允许而做不到，而是整个圈子慢慢摸索出来的“合理之道”。有人反驳：可不可能和合不合理是挂钩的，因为合理的范围就是被可能性的边界框死的。接着，另一位网友一语道破天机，抛开了所有抽象的概念：“当你不再死盯着像素，而是把注意力放在数据结构上时，大脑思考和动手执行之间的摩擦力就彻底消失了。”这句话比任何长篇大论的论证都要一针见血。

随后关于 TUI 与 GUI 的辩论就没那么哲学了，但也同样精彩。有人直截了当地问：现在硬件跑图形界面轻松得很，干嘛非要在 4K 屏幕上抠出一块地方来满屏画文本？答案是：图的就是那种用户体验。当你全屏都在画文本时，你反而画不了太多文本。显卡越来越强，3D 模型的多边形就越来越多；但 80 列宽、24 行高的终端窗口能活到现在，恰恰是因为“少即是多”。还有一派观点认为，TUI 的巅峰根本没过去。原文把 TUI 的黄金时代定在 70 和 80 年代。一位网友把它往后挪到了 90 年代初，那时候的 DOS 软件像 QBASIC 和 EDIT.COM 已经有了 VGA 显示、清晰的文本模式，还支持鼠标。诺顿指挥官和午夜指挥官算是那个时代的巅峰之作。还有人说巅峰就是现在，并且举了 Omarchy（一个纯终端操作系统）和现代终端里也能跑弹性盒子布局的例子。大家对巅峰期在哪有分歧，但对大方向的看法是一致的：文本界面身上就是有种魔力，能让人一次次回坑。

评论区也暴露了原文避而不谈的一些实际局限。最明显的硬伤：纯文本插不了图片。这就好比发短信（SMS）和发彩信（MMS）的区别。你可以放个图片链接，但链接早晚会失效。有人提议用 Base64 数据 URI[^13] 来曲线救国，但要是为了解码这玩意儿，还得去实现一整套图片格式的规范，那就彻底违背了纯文本简单纯粹的初衷。另一个更大但也基本没人能解答的问题是无障碍访问。对于用屏幕阅读器的人来说，用 ASCII 画图是不是纯纯的折磨？评论区没给出什么靠谱的答案。屏幕阅读器遇到一堆排成空间图案的制表符，读出来的八成全是乱码噪音。纯文本画图圈子在这方面确实有个大窟窿，需要更多的关注。

最后一个讨论彻底点明了这篇文章到底在聊什么，不在聊什么。有人问，为什么没提 draw.io？底下秒回：draw.io 是个图形化编辑器，画出来的是图形输出。文章里聊的这些工具，是“用文本画图”。它们输出的结果就是纯文本本身。这个区别就是整个问题的核心。由制表符拼出来的图表可以安安静静地待在代码注释里、README 文档里，或者终端屏幕上。它跟代码如影随形，不管你怎么换平台，它都能挺过来。而 draw.io 画的图虽然好用，但它是个以独立格式存在的额外文件。

整场讨论既力挺了文章的核心观点，又把事情搞得更复杂了。力挺在于，它证明了其实已经有很多人生活在这个“纯文本的未来”里了，他们自己做工具、记账、画图表，死心塌地捍卫着那种“随便找个编辑器就能打开文件”的自由。复杂在于，它也暴露出“纯文本”本身就是一个充满争议的概念，Unicode 并没有彻底终结编码大战，而且也根本没人认真想过，文本界面对那些看不见屏幕的人到底意味着什么。文章说得对，纯文本会一直陪着我们。但评论区告诉我们，我们身处的这个“当下”比文章写的要庞大和混乱得多，而想要让它长久地“留存”下去，我们要下的功夫，远比我们愿意承认的要多。

[^1]: Turbo Vision: Borland 公司在 1990 年代初推出的基于 DOS 字符界面的应用程序框架，它让纯文本界面也能有类似窗口、菜单、鼠标点击的图形化交互体验。
[^2]: 掀底牌 (pulled rugs): 原文用了 "pulled rugs"，取自英文俚语 "pull the rug out from under someone"（把某人脚下的地毯抽走），这里意指网友在评论区推翻了文章的预设或打破了一些固有认知，让人有种“幻灭”或重新审视的感觉。
[^3]: 哑终端模式 (dumb terminal): 早期计算机外设的一种状态，仅具备文本输入和显示功能，没有本地处理或图形能力。在 gnuplot 等绘图软件中，指用基础的英文字母和符号拼凑出数据图表。
[^4]: Code Page 437: IBM PC 最初的字符集，除了标准 ASCII 外，还包含了很多用于画表格的线框字符、阴影块和一些特殊符号，是很多经典 DOS 界面和字符画的基石。
[^5]: Roguelike: 一类角色扮演游戏，其早期经典的共同特征是完全使用 ASCII 字符来表示地图、怪物和道具（例如用 `@` 代表主角，用字母代表怪物）。
[^6]: 码位 (Code point) 与字形 (Glyph): 码位是字符在国际编码表（如 Unicode）中的数字编号，而字形是这个字符在屏幕上实际显示出来的图案模样（比如特定的字体设计）。
[^7]: BOM (Byte Order Mark): 字节顺序标记。这是一串放在文本文件开头的隐藏字符，用来告诉程序这个文本是用哪种具体方式编码的，但它经常会导致一些无法识别它的软件读取出错。
[^8]: PCL 打印流: 惠普开发的一种打印机控制语言。PCL 文件包含了用来指导打印机如何排版和绘制页面的指令。
[^9]: Unix 管道 (Unix pipelines): Unix/Linux 系统中的一种核心机制，允许把一个程序的输出结果直接当成下一个程序的输入，像流水线一样串联多个小工具来处理文本数据。
[^10]: 林迪效应 (Lindy effect): 一种经验规律，指一些不易损耗的事物（如技术、思想），它们存在的时间越长，未来能继续存活下去的预期寿命就越长。
[^11]: Beancount 与 Fava: Beancount 是一款基于纯文本的复式记账工具，一切账目全靠写代码一样的文本；而 Fava 是为它提供可视化 Web 报表界面的开源软件。
[^12]: ColorForth: 一种极其精简的编程语言，它的特色是使用不同的颜色来代替某些标点符号或语法关键词，以此来大幅压缩代码体积。
[^13]: Base64 数据 URI: 一种把图片等二进制文件转换成一长串纯文本字符（Base64 编码）的方法，这样就可以直接把图片数据嵌在文本代码里，不用再单独存一个图片文件。
