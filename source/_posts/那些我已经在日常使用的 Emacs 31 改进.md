Rahul Juliato 关于 Emacs 31 的文章开头用了一个巧妙的对照。不久前，Karthik Chikmagalur 刚发布了一份指南，介绍了目前 Emacs 中鲜为人知但已经内置的功能——也就是所谓的”开箱即用”。而 Juliato 想写的，是下个版本中即将迎来的新内置特性。几个月来，他一直通过编译 `emacs-31` 分支和主干代码，把这些新特性当成日常主力来用。他的配置文件名叫 Emacs Solo，不依赖任何外部插件。他记录的每一个变化，都是 Emacs 核心代码新吸收的特性，而这些以前都需要他自己手写代码来实现。正如他所说，看着 Emacs 不断进化，自己的配置文件随之越来越精简，这是“作为 Emacs 用户一种默默的喜悦”。这篇文章在 Hacker News 上引发的讨论不仅印证了这种喜悦，还揭示了一个更深层的现象：Emacs 31 绝不仅仅是一次普通的功能更新。这个项目正在以前所未有的速度吸收生态圈里最优秀的创意，并且向新一代可能早已把它打入冷宫的用户，重新证明着自己的价值。

最让人一眼惊艳的功能是 `tree-sitter`[^1] 的自动安装。多年来，要想在 Emacs 里用上 `tree-sitter`，你得手动配置源列表，调用命令安装，还得祈祷你的编译工具链别出幺蛾子，能顺利编译出语法文件。Juliato 的配置展示了现在的全新体验：只需两行代码就能省去所有繁文缛节——`(treesit-auto-install-grammart)` 和 `(treesit-enabled-modest)`。现在，`TypeScript`、`Rust`、`TOML` 和 `YAML` 等语言的语法源文件已经直接内置在相应的模式里了。评论区的反应简直像松了一大口气。有位用户贴出了一整段他终于可以删掉的 `csh` 脚本——那简直是个”鲁布·戈德堡机械”[^2]，需要先检测系统平台和架构，再从 GitHub 下载预编译的语法文件，最后解压到正确的目录里。他激动地写道：“哈利路亚，谢天谢地！”另一位用户则戏称这是”我 Emacs 配置的减肥神药”[^3]。

不过，讨论中也提到了 Juliato 指出的一些不完善之处。他提到了一个容易”搬起石头砸自己的脚”的设计：自动安装的语法文件并没有按系统架构区分开来。也就是说，`x86_64` 和 `arm64` 架构的文件会以同一个名字存放在同一个共享配置目录下。要在多机之间同步配置的用户可得小心了。评论者们还补充了另一个痛点：Windows 系统。在 Windows 上找预编译的语法文件一直都很让人头疼，几位用户直接表达了疑虑：这套自动安装机制在 Windows 上到底能不能跑得通？一位每天在 Windows、Ubuntu 和 macOS 之间来回切换的保守派跨平台用户问出了最发人深省的问题：“我该不该把 `tree-sitter` 加入我的工具流里呢？”帖子里的回答是明确的“应该”，但这问题本身也暴露了从源码尝鲜的早期玩家，与即将用到 Emacs 31 正式版的主流用户之间，依然存在着信息差。

Juliato 对 Emacs 31 最具个人色彩的贡献，是 `markdown-ts-mode`。这是一个实验性的内置模式，源于他 2025 年初发给 Emacs 开发者邮件列表的一份提案。他十分注重与 Stéphane Marks 分享这份功劳，Marks 后来加入并成为联合原作者，正是他把这个模式从“能用”提升到了“好用”的境界。这个模式的招牌功能是为 `Org-mode` 用户量身定制的，目的是让他们感到宾至如归：它采用了类似 `Org-mode` 的快捷键，可以轻松在标题间导航、折叠段落以及在文本结构间跳转。代码块不仅有高亮，而且会调用对应语言真正的”主模式”[^4]来渲染。比如一段 `Elisp` 代码块，显示出来的是原汁原味的 `Elisp` 语法高亮，而不是干巴巴的等宽字体。行内图片也能直接在文档里渲染显示。绝大部分代码块内的编辑命令都能正常工作，不过补全功能目前还不完善。

论坛里的讨论清晰地阐明了为什么这个模式在战略层面上如此重要。有位评论者一针见血地说：“整个开发者社区似乎并不认同 `Org-mode` 是最优秀的语法。”事实上，`Markdown` 已经赢得了更广阔的世界。拥有一流的、内置的 `markdown-ts-mode`，意味着 Emacs 在主动迎合用户现有的使用习惯，而不是强迫他们干什么都得去学 `Org` 语法。与此同时，也有另一位评论者反驳，提出了一个远超写代码范畴的 Emacs 愿景：“我们当中的一些人，用它来处理所有能用纯文本表现的东西：待办事项清单、日历、`RSS` 阅读器，甚至邮件客户端。”`Markdown` 和 `Org` 之间的路线之争不会就此消失，但 Emacs 31 显然比以前更好地服务了这两个阵营。

文章里被讨论最多的部分，其实并不是那些重磅功能，而是一些”创可贴式的修复”——那些解决了多年来困扰用户、逼得他们只能靠自己写补丁代码来对付的小痛点。全新的 `kill-region-dwim` 功能如果被设置为 `'emacs-word`，当没有选中文本区域时，按下快捷键就会向前删除一个单词，而不是像以前那样直接报错。一位评论者马上贴出了他以前专门为此写的自定义函数，并为终于能把它删掉感到一身轻松。另一个赢得了极大好评的小修复是：在运行基于 `curses` 库[^5]的程序时，终端终于不再吞行了。多年来，`htop` 和 `nethack` 这些程序在 Emacs 的终端模拟器里几乎没法用。而在 Emacs 31 中，终端画面终于能正确重绘了。Juliato 称这是他过去不得不用外部终端的最后几个理由之一。

可编辑的 `xref`[^6] 缓冲区这件事值得单独拿出来说说，不仅仅是因为功能本身，更是因为它展现了 Emacs 的开发模式。以前，Juliato 同样的代码搜索总是得跑两次：先用 `xref` 搜一遍看结果，然后再用其他命令跑一遍，为了拿到一个可以原地编辑结果的界面。2026 年 3 月，他提交了一个补丁提议，想加个命令把 `xref` 的结果塞进可编辑的格式里。`xref` 的维护者 Dmitry Gutov 抛出了一个更犀利的反问：为什么不直接在 `xref` 缓冲区里就地编辑呢？几天后，Gutov 就写好并提交了相应的编辑模式。它彻底干掉了多余的步骤，而且在处理大量搜索结果时运行得更快。Juliato 原来的想法最终也作为一个可选命令被纳入，但真正落地的核心功能，比他最初的提议要好得多。正如他所写：“维护者问到了点子上。”这样一个闭环——用户自己动手解决痛点，维护者重新审视问题本质，最终诞生更优解——正是支撑 Emacs 几十年长盛不衰的协作引擎。

有关终端的精彩故事并未在文章中全部交代。评论区里提到了 `Ghostel`，这是一个新的 Emacs 终端模拟器，其性能远超旧版方案：吞吐量达到了 75 MB/s 对比 18 MB/s；打印文件的测试只需 220 毫秒对比 550 毫秒。就在这场讨论发生的同一天，它的伪终端模块就被剥离出 Emacs 主线程并合并了。除了单纯的快，`Ghostel` 在运行像 `Claude Code`、`btop` 这些现代终端界面时表现也极佳，它能很好地处理备用字符，从而消除了界面动画中的闪烁问题。它还增加了一些对命令行 AI 至关重要的体验升级：Claude 思考时状态栏会有加载动画，AI 运行结束会有通知提示，支持可点击的超链接，还能拖拽文件。Juliato 的文章庆贺了 `htop` 不再被吞行的修复。而讨论则表明，Emacs 里的终端演进早已超越了单纯的修补，开始迈入一个新境界：Emacs 自带的终端模拟器正在成为 AI 辅助工作流中的一项核心竞争优势。

新加入的窗口布局命令也赢得了满堂彩。转置、顺时针旋转、左右翻转、上下翻转。一位评论者直言这简直是“梦想照进现实”。另一位用户则很期待看到原生的框架转置功能与 `Pure GTK` 编译版会碰撞出怎样的火花。速度栏（`speedbar`）的改变——现在可以作为一个侧边窗口停靠，而不是飘在外面当悬浮框——让一位用户感叹终于可以把第三方的 `sr-speedbar` 插件扫地出门了。这些改进都很微小，但都在强化 Juliato 的核心论点：少用第三方插件，让配置更简单。

性能问题像背景音乐的低音节拍一样，贯穿了整个讨论。文章本身对这个话题避而不谈，但评论区可没闲着。一位用户抱怨在 macOS 上跑 Emacs 要花 45 秒才能启动，直呼这毛病“病入膏肓”。另一位老兄马上反驳说自己的 macOS 上启动只需两秒。而在 Windows 系统上，评价则是出奇一致的“慢如老牛”。标准的“解药”是配合客户端开启守护进程，这能让客户端的打开和关闭瞬间完成。有评论指出，`GCMH`（垃圾回收魔法黑客）这个插件对于解决那套三十年前的默认垃圾回收机制导致的卡顿至关重要，再配合原生编译，剩下的性能短板也就补齐了。现在的性能表现可以说是参差不齐：有人痛不欲生，有人坚持说 Emacs 很快；其实解决办法就在那里，只是新手往往缺乏这些圈内知识。

最引人深思的一条长帖，抛出了一个文章没直接问的问题：都 2026 年了，还有人在用 Emacs 吗？图啥呢？大家的回答勾勒出了一个“打死也不肯被替代”的编辑器形象。有个用户曾为了更好的 AI 集成短暂跳槽到了 `VSCode`，但当 Claude 在 Emacs 里也能顺畅运行后，立马又乖乖跑回来了——吸引他回来的，是屏幕上极高密度的代码展示能力：4K 显示器上竖着排开三个窗口，有时还要再劈成两半，同时并行处理多达六个上下文。另一位用户把项目的复兴归功于 `tree-sitter`：“当项目能把精力集中在通用的底层工具上，而不是让每个语言社区各自维护代码时，就好比好钢用在了刀刃上。”`Magit`[^7] 被反复点名，被公认为不可或缺的神器。有个用户说他在 `Org-mode` 的表格里做账单。另一个人直接拉了张清单：在 Emacs 里刷论坛、在 `Org-mode` 里看工作消息、看视频还能用按键控制，甚至直接对屏幕截图做文字识别、控制浏览器标签页。对这些神人来说，Emacs 早就不是什么代码编辑器了。它是人机交互的终极统一文本界面。

AI 融合是文章中只字未提，但在评论区却无处不在的”房间里的大象”。大家纷纷点名几个主流插件，认为正是它们让 Emacs 具备了与 `VSCode` 拼 AI 功能的实力。有评论形容这些插件用起来就像 Claude 官方终端，有的则几乎还原了 `Cursor` 编辑器的幻影补全和对话功能。另一个人指出，Emacs 与基于命令行的 AI 工具简直是天作之合，这意味着 Emacs“永远也不会淘汰”。前面关于 `Ghostel` 终端的讨论直接呼应了这点：它的加载动画和通知弹窗，本来就是专门为命令行 AI 代理打造的。整个讨论都在传递一个信号：AI 融合对 Emacs 来说不是威胁，而是助推器。基于命令行的 AI 工具天然契合 Emacs 的架构，而社区插件正以肉眼可见的速度，抹平与其他编辑器在图形化 AI 体验上的差距。

当然，并非所有人都被这种狂热气氛所感染。有几位评论者泼了冷水，认为文章里欢呼的那些新功能“实现起来简单得很”，插件明明很好装也很好配。但文章中暗含的反驳理由是：真正的价值，恰恰在于让你不用装外部插件、不需要动手写配置，就能跑起来。一位老资历用户说出了怀疑论者的心声：“我很欣慰还有人在开发 Emacs，毕竟我天天都在用它。但我必须说，我个人大概率用不上这篇文章里提到的任何新东西。”另一个人也开玩笑说，他就算升级到 31 版，转头也会把新功能忘光，继续用二十年前的老办法使用 Emacs。这些声音也在提醒我们，Emacs 的受众群体简直宽得离谱：这里有把所有赛博生活都搬进编辑器的极客狂人，也有只要语法高亮和 `Git` 功能就别无所求的极简主义者。

夹在怀疑论者和狂热粉丝中间的，是一群这篇文章几乎完美命中靶心的群体：脱坑的老用户。好几个评论者说自己从 2000 年代初以后就没正儿八经动过配置文件了，现在正迫切需要一份指南来补课。大家都夸赞这篇原帖正是这群老用户需要的桥梁：它由一个身处技术最前沿的玩家执笔，帮你梳理了最新内置的特性，并且清楚地解释了每一个改变能帮你省掉哪些折腾代码。

在文章结尾，Juliato 解释了自己为什么要把未发布的 Emacs 版本当成日常主力：“我想知道盒子里到底装了什么新东西，而了解未来的最好办法，就是亲身活在未来里。”围绕他这篇文章的讨论证明了一件事：这个盒子的扩容速度，远超很多用户的想象。`tree-sitter` 的自动安装铲平了普及现代语法高亮的最大障碍。`Markdown` 模式兼顾了广泛的开发者习惯，同时也没丢掉自身的编辑灵魂。可编辑的 `xref` 缓冲区则证明，项目的协作式开发依然能酝酿出极其优秀的特性。至于周边的生态环境，正在填补核心功能尚未触及的盲区，而且迭代势头极猛。Emacs 31 不是什么翻天覆地的革命。它是一次次微小进步的厚积薄发。它让这个编辑器在每次迭代中，都能帮你少写几行胶水代码；它也向世人展示，这个社区仍在为未来的路该怎么走，持续提出正确的问题。

[^1]: tree-sitter：一种现代的解析器生成工具和增量解析库。它可以为源代码快速构建具体的语法树，在现代编辑器中常用于实现高精度的代码高亮、代码折叠和结构化编辑。
[^2]: Rube Goldberg machine：鲁布·戈德堡机械，指一种被设计得过度复杂、用迂回曲折的方法去完成极其简单任务的机械装置。常用来比喻过度设计、冗长繁琐的代码或工作流程。
[^3]: GLP1：一类原本用于治疗糖尿病的药物（如司美格鲁肽），因其极度显著的减肥效果而爆红。这里是一种幽默的比喻，指新功能让庞杂臃肿的 Emacs 配置文件成功“瘦身减脂”。
[^4]: major mode：主模式。Emacs 中的一个核心概念，指针对特定类型的文件（如 C 语言、Python 代码、纯文本等）提供特定的编辑行为、快捷键和语法高亮的独立环境。通常每个编辑区域只能同时激活一个主模式。
[^5]: curses：一个提供在终端环境下控制字符光标移动、绘制文本界面的编程库。像 `htop` 等带有简单图形界面的终端监控程序，其底层通常依赖此类库。
[^6]: xref：Emacs 中的一个内置交叉引用工具，常用于在庞大的代码库中快速查找函数定义、变量引用和跳转。
[^7]: Magit：Emacs 中一个极其强大的 Git 客户端插件，以其纯键盘操作、高度流畅和直观的工作流闻名，被许多开发者认为是目前最好用的 Git 图形/文本界面交互工具之一。
